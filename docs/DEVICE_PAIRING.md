# 扫码新增设备：开发版本说明

这是基于已验证 main `5a1d5328114783fc13d6ef4664c3efb9726bd327` 的独立开发源码，尚未发布或部署。不要将其当成已上线的 v0.2.3 功能。

## 使用流程

1. 在已用密码登录的网页打开“设备与登录”，生成二维码。
2. 在 Android App 登录页选择“扫描网页二维码，配置并登录”；其他原生平台可使用粘贴配对内容入口。
3. App 显示目标服务器地址及权限说明，用户确认后认领二维码。
4. 对照网页与 App 的六位校验码。在网页核对设备名称，输入当前 owner 密码并批准。
5. App 使用独立的临时证明兑换独立设备会话，自动配置服务器 URL 和当前账户；现有邮箱由服务端载入。
6. 网页的设备列表可撤销该设备，后续 API 请求立即失效。

目前是单 owner 产品，批准设备意味着完整邮件及设置权限。设备没有新增设备的批准权限；它不能用刚领取的设备 token 创建或批准下一次配对。网页授权只对当前认领者生效。二维码两分钟内有效，单次使用；原网页会话退出或过期会使尚未兑换的配对失效。

本阶段登录令牌仅在内存，最长八小时。重启 App 后需要重新登录；没有新增长期 refresh token、安全存储、生物识别解锁或通行密钥。平台生物识别及标准 WebAuthn 属于后续阶段，不能用本阶段测试推断其已经支持。

## 部署前提

- 配置 `MAIL_ALLOWED_ORIGIN` 为用户实际可达的规范 HTTPS 源，例如 `https://mail.example.com`，不得带路径、查询参数或末尾 `/`。二维码地址由该配置产生，不采信外部请求的 Host 或转发头。
- 客户端 API 地址使用 `https://mail.example.com/api/v1`。支持明确的 HTTPS 端口和受信任 TLS 的自托管内网部署，不绕过证书错误。
- 原生端可手工填写服务器 URL；扫码会自动填写。服务器变更不会沿用旧服务器 bearer。
- Android 相机权限在用户打开扫描器时由系统处理；拒绝权限仍可返回并粘贴配对内容。相机不会在普通登录页后台启动。
- Android 的正式签名、安装包发布、真机相机验收尚需完成；Windows 编译及安装包也需 Windows 工具链。工程目录存在不等于原生安装包已经验收。
- 不在二维码中传递密码、邮箱服务商 OAuth 凭据或长期 token；不要把一次性二维码放进日志、公开截图或分享链接。
- 网络中断导致兑换结果不明时，不重复兑换同一个事务。回网页核对并撤销可能已建立的设备，然后生成新的二维码。

## 安全与兼容性

服务端仅保存二维码 secret 的 SHA-256 和 App 验证器的 S256 challenge；App 验证器从不出现于二维码。创建、认领、批准、拒绝、兑换、退出及撤销有明确的事务边界，防止重复授权和竞争条件。

数据库 V6 使用独立的配对、设备及 token 映射表，保留旧 access_token 两列结构。升级前仍应备份数据库；不得凭表结构兼容就声称旧应用支持设备权限边界或安全回滚。

实际注册用户设备或启用长期访问须由用户在目标设备与网页交互批准。开发测试仅使用隔离演示数据，不连接真实邮箱或真实生产账户。

## 开发验证

- 服务端：`mvn -f server/pom.xml test`，并使用独立临时 PostgreSQL 重跑数据库相关测试。
- Flutter：`flutter analyze`、`flutter test`、`flutter build web --release --no-web-resources-cdn`。
- 跨语言合成契约：运行已明确开启 demo 的 loopback 服务，将 `MAIL_ALLOWED_ORIGIN` 配置到其实际端口，再执行 `dart run tool/live_device_pairing_smoke.dart http://127.0.0.1:端口/api/v1`。脚本先验证 loopback 和 health.demoMode，才会执行合成授权。
- 二维码相机、真实系统权限弹窗、Android 正式签名、Windows Hello 与硬件安全密钥不可由纯 Flutter widget 测试替代。

接口、状态和保护约束见 [配对契约](DEVICE_PAIRING_CONTRACT.md)。最终完成状态以本开发版本的验证记录为准，不沿用旧发布的测试数量。
